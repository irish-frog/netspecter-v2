# Settings maintenance controls

Settings → Maintenance provides a preview of traffic-only reset, all collected-history reset, retired IDS purge, or a combined selection. GET never queues work. A signed-in administrator with login enabled must submit CSRF-protected forms. Apply requires a recent unused preview, the exact appliance hostname, a deletion acknowledgement and the existing administrator password (normal login throttling applies). The password is checked in the web process and never enters the request/status files.

The web process atomically queues a complete, bounded fixed-schema request. A systemd path activates a root oneshot outside the web/collector processes. Requests permit only reviewed scope/purge enums, UUIDs and local hostname, never paths, commands, package names or arbitrary arguments. Root-owned state lives outside the web-writable data directory. Per-job status remains available across web restarts and concurrent queued previews, bounded to32 summaries/private failure logs. No new listener or sudoers rule is added. Disabling normal login disables maintenance controls too.

The root worker builds a preview from the existing schema-gated reset service and a fixed Suricata package simulation. It revalidates before apply. A root-owned operation lock serializes the entire apply (preflight, DNS snapshot, removal, reset and final verification) with UI updates and manual reset/recovery commands. The reset child inherits the lock descriptor explicitly; its root-only CLI verifies the descriptor matches the fixed root-owned lock inode. Preview also takes the lock to avoid inspecting a concurrent update.

Purge includes installed or residual-config suricata/suricata-update only. It refuses incomplete package states or simulations involving other removals. Actual removal uses dpkg --purge with exactly those fixed package names, dependency checks enabled, no force flags and no autoremove. Thus a changed package-manager state cannot expand the transaction to unrelated dependency removals; a package-manager conflict fails instead. The updater may fail with a busy notice and can be retried after maintenance.

History cleanup reuses the coordinated stop/backup/stage/integrity/swap/recovery/start workflow. It also pauses/resumes the maintenance request watcher while retaining the executing root worker. Settings, credentials, licence, edited names, operator rules and existing backups remain. Traffic-only scope retains NetSpecter DNS, quality, speed-test and other non-traffic history. All-history scope clears collected NetSpecter histories but keeps native AdGuard query logs, filtering/settings and operating system logs. Temporary reset rollback copies are discarded only after successful service verification.

The worker checks DNS configuration hashes and, when AdGuard was active, UDP/TCP resolution before/after; passive deployment readiness is checked before changes and afterward. It never restarts AdGuard or alters bridge forwarding. Failure is visible in Settings; private subprocess output is kept in a bounded root-only log. A reset recovery marker requires root-shell recovery, and neither updater nor a new reset is allowed to overwrite an interrupted reset. Preview/worker failures do not automatically apply or retry a cleanup.

The legacy passive-mode Clear Traffic route redirects to these controls, avoiding its incomplete modern-flow reset. Merely installing/updating this feature never clears history or purges packages. Do not trigger a real cleanup on the held client. Owner deployment adds the UI only; no production reset/purge is part of feature verification.

Validation includes real request ownership/symlink/size checks on Linux, atomic no-clobber queueing, recent-preview consumption/replay refusal, CSRF/auth/password/hostname/acknowledgement, package allowlist/dependency simulation, DNS failure blocking deletion, inherited whole-operation lock, preserved database rows, and actual disposable-CI systemd preview → lock-contention refusal → traffic reset → watcher restart/fresh collection. Adversarial review found and corrected operation-lock gaps, residual configurations and package-simulation races; re-review found no further material issue.

## Preview/confirmation usability correction

A real owner report was confirmed as kind=preview/status=ready, scope=traffic, purge_ids=true; no apply had occurred. Confirmation is now placed before the selection form and explicitly says nothing has been cleared. The selection remains sticky and is available under Change selection; button labels distinguish clearing all history from traffic-only. Expired/replaced previews are refused in the UI and backend. Per-job progress supports a manual result link and HTTP refresh when JavaScript polling cannot complete.

A reproduced auth/setup routing inconsistency redirected the direct maintenance page and blocked its status API when mandatory setup fields were incomplete, although the Settings alias was allowed. Both endpoints now share Settings' setup exemption while retaining admin authentication, enabled login, CSRF, password, hostname and acknowledgement checks. This does not exempt them from login or authorize any automatic cleanup. Regression tests reproduce the setup case and exercise confirmation order, sticky all-history scope and non-JavaScript progress. No root worker, package removal or reset semantics changed.
